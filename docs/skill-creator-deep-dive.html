§01

The substrate: what a skill actually is

Before the creator, the created. A skill is a folder that teaches a model a job — priced in tokens.

A skill is a directory with one required file, SKILL.md — YAML frontmatter (name, description) above Markdown instructions — plus optional bundled resources: scripts/ for executable code, references/ for documentation loaded on demand, assets/ for files used in outputs. That's the whole format. What makes it interesting is not the format but the economics: everything a model reads competes for a finite context window against the user's actual task.

Skills resolve this with progressive disclosure — a three-level loading scheme where cost scales with commitment. Metadata is the standing cost paid on every session; the body is paid only when the skill triggers; bundled resources are paid only if the work demands them. And executable scripts break the pattern entirely: code executes without ever entering context.

Mechanism · the three levels

L1 — metadata, always in context. Name + description of every installed skill, ~100 tokens each. This is the only thing Claude sees when deciding whether to use a skill.

L2 — body, on trigger. The SKILL.md Markdown loads when Claude invokes the skill. Guidance: under 500 lines SKILL.md:96; the platform docs and the agentskills.io spec say under ~5k tokens.

L3 — resources, on demand. Reference files load only when a specific step needs them; scripts execute without loading; assets are consumed by tools, not read. Unlimited, because unpaid until used.

Rationale · why lazy-load prose

The context window is shared infrastructure — the older skill-creator called it "a public good," and the platform docs still do. A skill that loads 10k words up front taxes every task, including the ones it can't help with. Progressive disclosure lets an organization install dozens of skills at ~100 tokens apiece and pay full price only for the one that's actually doing work. It also explains an editorial rule you'll see throughout: all "when to use this" language belongs in the description (L1), because by the time L2 is loaded, the when-question has already been answered.

One more consequence of the levels worth internalizing: in stage 3 of the ledger above, the grader instructions (agents/grader.md) never touch the main context at all — they load inside a subagent's context. Skills that orchestrate subagents get a fourth, free tier: prose that's read by someone else.

§02

The specimen: skill-creator's own anatomy

The best way to see the doctrine is to notice that skill-creator is built out of it.

Eighteen files, ~227 KB. Only one of them — SKILL.md, 33 KB — is ever loaded into the main context as instructions. Three agent playbooks and one schema reference sit behind on-demand reads. Everything else is machinery: eight Python scripts that execute, two HTML templates that get filled in and served, and a license that ships in the package. Click through the tree; each file is tagged with the disclosure level it lives at.

Rationale · determinism where it's cheap, judgment where it's needed

Notice what got turned into code. Statistics (aggregate_benchmark.py), zip packaging, YAML validation, subprocess orchestration, HTML generation — anything with one right answer is a script, because a script is deterministic, reusable, and token-free. What stayed prose is exactly what needs judgment: how to grade evidence, how to compare blind, how to interview a user. The skill draws the line between the two on empirical grounds (see §04's "bundle what every run reinvents") rather than taste.

§03

From style guide to laboratory

skill-creator is on its second philosophy. The git history of anthropics/skills shows exactly when — and what — changed.

The first skill-creator (October 2025) was a writing guide: a 357-line document of authoring doctrine — "Concise is Key," "Set Appropriate Degrees of Freedom," what files not to create — plus an init_skill.py scaffolder and a packager. It told you how a good skill should read.

On 2026-02-24, commit 3d59511 replaced it nearly wholesale. The scaffolder and the doctrine chapters vanished; in their place arrived subagent playbooks, an eval harness, a benchmark aggregator, a human review UI, and a description-optimization loop. The new question isn't "does this skill read well?" but "does this skill measurably beat not having it?" The theory didn't die — it migrated into Anthropic's platform best-practices docs. The skill became the laboratory.

Rationale · why the voice changed too

The rewrite didn't just change the machinery — it changed the register. The old version spoke in impersonal imperatives; the new one says "Cool? Cool." SKILL.md:30, jokes about plumbers opening terminals SKILL.md:34, and signs off with "Good luck!" SKILL.md:485. That's not decoration: the skill's own writing advice is to explain reasoning rather than issue commands, to use theory of mind, to trust that "today's LLMs are smart" SKILL.md:302. The document practices the style it prescribes — it is its own best example.

§04

The core loop

Not a linear pipeline — a cycle with a human inside it, and an explicit instruction to join wherever the user already is.

SKILL.md states the loop twice — once at the top, once at the bottom, "repeating one more time … for emphasis" SKILL.md:472. Between drafts and packaging sits the part most skill-writing advice skips: run the skill against real prompts, with a baseline, and let the human judge the outputs before the model self-corrects. The stages below are clickable; the orange arc is the part that repeats.

Mechanism · who is this loop for?

The skill opens with audience calibration, not process. It warns that Claude's power "is inspiring plumbers to open up their terminals, parents and grandparents to google 'how to install npm'" SKILL.md:34 — and then draws a precise jargon ladder: "evaluation" and "benchmark" are borderline-acceptable; "JSON" and "assertion" require "serious cues" that the user knows them before you may use them unexplained SKILL.md:38-39. A skill that will be operated by a model on behalf of anyone has to encode not just what to do but how to talk about it.

Rationale · why prompts come before assertions

Test cases are saved to evals/evals.json as prompts only — assertions are deliberately deferred to run-time SKILL.md:145. Two reasons. First, latency: the runs take minutes, so assertion-drafting is scheduled into the wait ("don't just wait for the runs to finish" SKILL.md:201). Second, epistemics: you write better checks after committing to what the test should prove, but before seeing what the model actually did — the same pre-registration logic experimental science uses.

§05

The evaluation machinery

A subagent laboratory: parallel runs against a baseline, evidence-based grading, variance-aware aggregation — and a browser UI that puts the human before the model.

The workspace

Every run lands in a directory tree beside the skill — created lazily, iteration by iteration. Eval directories get descriptive names, not eval-0, so results stay legible SKILL.md:188:

my-skill-workspace/            ← sibling of the skill directory
├── skill-snapshot/            ← frozen copy, when improving an existing skill
├── iteration-1/
│   ├── fill-w9-from-csv/      ← one directory per test case, named for what it tests
│   │   ├── eval_metadata.json ← prompt + assertions
│   │   ├── with_skill/
│   │   │   ├── outputs/       ← what the subagent produced (+ metrics.json)
│   │   │   ├── timing.json    ← tokens + wall-clock, captured from the task notification
│   │   │   └── grading.json   ← the grader's verdicts + evidence
│   │   └── without_skill/     ← the baseline: same prompt, no skill (or the old version)
│   ├── benchmark.json         ← aggregated stats (+ benchmark.md for humans)
│   └── feedback.json          ← the human's comments, from the review UI
└── iteration-2/               ← the loop, again
Mechanism · three rules that make the data trustworthy

Spawn everything in the same turn. With-skill and baseline subagents launch together, "so it all finishes around the same time" SKILL.md:171 — no drift between conditions, no forgotten baselines.

Capture timing immediately. total_tokens and duration_ms arrive only in the task-completion notification and are "not persisted anywhere else" SKILL.md:219 — miss it and the cost data is gone. Ephemeral telemetry gets written to timing.json the moment it appears.

The baseline depends on intent. New skill → baseline is no skill. Improving an existing one → snapshot it first (cp -r) and run the old version as baseline SKILL.md:185-186. You can't claim improvement without the counterfactual.

The grader: two jobs, one burden of proof

agents/grader.md gives the grading subagent a double mandate: grade the outputs, and critique the evals themselves — "a passing grade on a weak assertion is worse than useless — it creates false confidence" grader.md:9. The verdict rules are miniature jurisprudence:

PASS: clear evidence the expectation is true AND the evidence reflects genuine task completion, not just surface-level compliance … When uncertain: the burden of proof to pass is on the expectation.

agents/grader.md:39, 99 — no partial credit; a right filename with wrong content is a FAIL

Beyond the listed assertions, the grader extracts claims the executor made — factual ("the form has 12 fields"), process ("used pypdf"), quality ("all fields filled correctly") — and verifies each against the artifacts, flagging what can't be verified. It also reads user_notes.md, where the executor confesses uncertainties and workarounds. The output feeds back on the eval suite itself via eval_feedback: the standard for a suggestion is whether the eval's author would say "good catch" grader.md:79 — the goal is discriminating assertions, ones that "pass when the skill genuinely succeeds and fail when it doesn't."

Fine print · exact field names or the viewer shows zeros

grading.json expectations must use text / passed / evidence — not name/met/details SKILL.md:225. Likewise benchmark.json needs configuration (not config) with pass_rate nested under result schemas.md:305. The schemas file exists precisely because a model regenerating these files from memory will drift; the viewer reads field names literally. Loose prose upstream, rigid contracts downstream.

Aggregation: variance or it didn't happen

aggregate_benchmark.py walks every grading.json, computes mean, sample standard deviation (n−1), min and max for pass rate, wall-clock and tokens per configuration, and emits the delta. Three runs per configuration is the default — enough to expose flakiness, cheap enough to actually run. The chart below renders the exact worked example from references/schemas.md:

Mechanism · the analyzer's five-way assertion taxonomy

After aggregation, an analyst pass (agents/analyzer.md) classifies every assertion across all runs: always passes in both configs → non-discriminating, dead weight; always fails in both → broken or beyond the model's capability; passes with skill, fails without → this is where the skill earns its keep; fails with skill, passes without → the skill is actively hurting; highly variable → flaky eval or non-deterministic behavior. In benchmark mode the analyzer is explicitly forbidden from suggesting skill improvements — observation and repair are separate steps with separate mandates analyzer.md:271.

The viewer: human judgment, front of the line

Once runs are graded and aggregated, eval-viewer/generate_review.py assembles a self-contained review page — outputs embedded as base64, spreadsheets rendered as tables, PDFs inline — and serves it on port 3117 (or writes a static file for headless environments). Two tabs: Outputs, one test case at a time with a feedback box that autosaves; Benchmark, the quantitative story. From iteration 2 on, it shows the previous iteration's output and the reviewer's previous comments beside the new result. Empty feedback is a signal too: "the user thought it was fine" SKILL.md:282.

This is the one place the otherwise-conversational SKILL.md resorts to capitals: "GENERATE THE EVAL VIEWER BEFORE evaluating inputs yourself … Sorry in advance but I'm gonna go all caps here" SKILL.md:451 — a self-aware exception to its own anti-caps rule, deployed because field experience showed Claude in Cowork skipping the human review and self-correcting instead. The apology is doing real work: it marks the rule as hard-won, not stylistic.

Rationale · why a human gate at all?

The model wrote the skill, ran the skill, and graded the skill — every quality signal so far is self-referential. The viewer breaks the circle. It's also deliberately not bespoke: "use generate_review.py … there's no need to write custom HTML" SKILL.md:249, because a standard UI with stable file contracts (feedback.json) is something the next iteration can read programmatically.

Advanced: the blind protocol

For "is the new version actually better?" questions, a stricter instrument exists. The blind comparator receives two outputs labeled A and B — it is never told which skill produced which — builds a task-specific rubric (content: correctness, completeness, accuracy; structure: organization, formatting, usability; 1–5 each, scaled to a 1–10 overall), and must pick a winner; "ties should be rare" comparator.md:85. Assertion pass-rates are explicitly demoted to secondary evidence. Only after the verdict does the post-hoc analyzer unblind: it reads both skills and both transcripts, scores instruction-following 1–10, and produces improvement suggestions prioritized by a single test — would this change have flipped the outcome? analyzer.md:85

Fine print

Blind comparison requires subagents and is labeled optional: "most users won't need it. The human review loop is usually sufficient" SKILL.md:329. The separation of concerns is the transferable idea: judge quality blind, diagnose causes unblinded — the same reviewer can't do both without the verdict contaminating the diagnosis.

§06

Triggering, and the description optimizer

The description is ~100 tokens standing between a skill and every task it will never be asked to do. skill-creator treats it as a measurable ML artifact — with a train/test split.

Recall the economics: at decision time, Claude sees only name + description in its available_skills list. And there's a documented bias to fight — "currently Claude has a tendency to 'undertrigger' skills" SKILL.md:67 — so descriptions should be written a little "pushy". The skill's own example:

Before: "How to build a simple fast dashboard to display internal Anthropic data."

After: "… Make sure to use this skill whenever the user mentions dashboards, data visualization, internal metrics, or wants to display any kind of company data, even if they don't explicitly ask for a 'dashboard.'"

SKILL.md:67 — the after-version names intents and phrasings, not features

There's a second, subtler mechanic: triggering scales with task complexity. "Claude only consults skills for tasks it can't easily handle on its own — simple, one-step queries like 'read this PDF' may not trigger a skill even if the description matches perfectly" SKILL.md:398. A perfect description cannot make a trivial query trigger; eval queries must be substantive enough that consulting a skill would actually help.

Designing the trigger eval: near-misses are the test

The optimizer starts from ~20 human-approved queries — 8–10 that should trigger, 8–10 that should not. The guidance on realism is unusually concrete: queries need "file paths, personal context … column names and values, company names … A little bit of backstory. Some might be in lowercase or contain abbreviations or typos" SKILL.md:348. The canonical good example, verbatim:

"ok so my boss just sent me this xlsx file (its in my downloads, called something like 'Q4 sales final FINAL v2.xlsx') and she wants me to add a column that shows the profit margin as a percentage. The revenue is in column C and costs are in column D i think"

SKILL.md:352 — versus the useless "Format this data"
Rationale · why the negatives matter more

"'Write a fibonacci function' as a negative test for a PDF skill is too easy — it doesn't test anything" SKILL.md:358. The valuable negatives are near-misses: adjacent domains, shared keywords, cases another tool should win. A description that only clears obvious negatives will false-trigger in production, silently taxing unrelated tasks with a 7k-token body load. The human signs off on the eval set through a purpose-built editing UI (assets/eval_review.html) before any optimization runs — "bad eval queries lead to bad descriptions" SKILL.md:373.

Mechanism · three details worth stealing

The UUID suffix. The decoy is named <skill>-skill-<8-hex>, so a substring match in the streamed tool-call JSON is unambiguous — it can never collide with a real installed skill.

Early verdict from the stream. With --include-partial-messages, the probe watches raw stream events: the first content_block_start naming any tool other than Skill/Read is an instant no; the decoy's name appearing in accumulated input_json_delta fragments is an instant yes — before the tool even executes. Verdicts in seconds, not tool-run minutes.

The CLAUDECODE strip. The env var guarding against nested interactive sessions is removed for the subprocess — the guard exists for terminal conflicts, and a programmatic probe has none run_eval.py:80-83.

The optimization loop: gradient descent by prompt

run_loop.py wraps the probe in a five-iteration improvement cycle with genuine ML hygiene. The eval set is split 60% train / 40% held-out test, stratified by should-trigger, seed 42. Each iteration: measure the current description on everything → if any train query fails, ask Claude (via claude -p) for a better description → repeat. The improvement prompt sees the failures, the false triggers, and every previous attempt with scores ("do NOT repeat these — try something structurally different") — but test results are stripped from what the improver sees, and the final winner is chosen by test score, "to avoid overfitting" SKILL.md:394. Rationale · the anti-overfitting quartet

Four independent defenses against the same failure: (1) the holdout split — 40% of queries never influence improvement; (2) blinding — test scores are filtered out of the improver's prompt (run_loop.py:195 strips every test_* key); (3) the prompt itself — it forbids "an ever-expanding list of specific queries" and demands generalizing "to broader categories of user intent," partly because the description is injected into every conversation and bloat is a standing tax improve_description.py:127-132; (4) selection by test. The same discipline the skill preaches for skill bodies — generalize from feedback, don't patch the example — implemented mechanically for descriptions.

Fine print · the budget and the safety net

Descriptions target 100–200 words with a hard 1024-character ceiling (over it, truncation). If the improver overshoots anyway, improve_description.py makes one fresh rewrite call quoting the too-long attempt improve_description.py:163. The loop is told to test with the session's own model ID "so the triggering test matches what the user actually experiences" SKILL.md:390 — trigger behavior is model-dependent, and optimizing against the wrong model measures the wrong thing. A live HTML report (auto-refreshing every 5s) opens the moment the loop starts, so the human watches iterations land in real time.

§07

Guardrails: validation and packaging

The prose is permissive; the pipeline is not. Before anything ships, quick_validate.py gets a veto.

package_skill.py refuses to zip anything that fails validation. The rules below are the real ones from quick_validate.py — plus two that exist only in the platform docs, flagged separately. Try them live; the form starts deliberately broken:

The one-SKILL.md rule

The local validator adds a check absent from the upstream repo (the installed copy is ahead of GitHub here): a package must contain exactly one SKILL.md, at the root. The in-code rationale: "The Skills API and claude.ai accept exactly one per skill — only Claude Code's filesystem loads nested ones" quick_validate.py:38-42. And because failure modes deserve exits, the error message ships three remedies: separate skills → package individually or build a plugin; supporting docs → rename to references/<topic>.md; swept in by mistake → package only the one directory.

What a .skill file is

A zip with a different extension. package_skill.py validates, then deflate-compresses the folder, excluding __pycache__, node_modules, *.pyc and .DS_Store at any depth — and evals/ only at the skill root package_skill.py:19-24. That last nuance is deliberate: your test suite stays with the source, but doesn't ship to every consumer. Presenting the file is itself gated on capability: package-and-present only runs if a file-delivery tool exists in the session (present_files, or SendUserFile in Cowork), where the file card can show a Save skill button that installs directly into the user's profile SKILL.md:410-416.

Fine print · two frontmatter dialects

The validator enforces the open-standard field set (agentskills.io) — the one uploads to claude.ai and the Skills API accept. Claude Code's own loader understands many more fields (when_to_use, disable-model-invocation, user-invocable, model, context: fork, hooks, …), every one of which quick_validate.py would reject as an "unexpected key." The validator is aligned to the portable format, not the platform's superset — write a Claude-Code-specific skill and the packager becomes your adversary.

§09

Tensions in the doctrine

Read skill-creator against Anthropic's own docs and spec, and the disagreements become the most instructive part.

None of these are bugs, exactly. They're strata — a fast-moving skill, slower-moving docs, and an externalized spec, each written at a different moment of belief. Five worth knowing:

1 · Should instructions shout?
skill-creator"If you find yourself writing ALWAYS or NEVER in all caps … that's a yellow flag — reframe and explain the reasoning … more humane, powerful, and effective." SKILL.md:302
platform best-practicesRecommends "stronger language such as 'MUST filter' instead of 'always filter'" when compliance matters.
Read: a live philosophical split about steering models — explanation vs. emphasis. skill-creator bets on theory of mind, then breaks its own rule exactly once, with an apology, where field data showed explanation failing (§05's viewer rule). Emphasis as the exception is perhaps the actual doctrine.
2 · How big may a body be?
docs + agentskills.io specSKILL.md body under ~5k tokens (older skill-creator: "<5k words").
skill-creator today"<500 lines ideal" and "feel free to go longer if needed" SKILL.md:90-93 — while itself weighing 5,166 words ≈ 7k tokens, the largest SKILL.md in the anthropics/skills repo.
Read: the ceiling loosened as models got better at long instructions — and skill-creator, a genuinely complex workflow, spends its budget deliberately. The 485-line count still slips under its own 500-line rule. Lines were chosen over words; both are proxies for tokens.
3 · When does a reference file need a table of contents?
docs + specOver 100 lines → include a ToC.
skill-creatorOver 300 lines → include a ToC SKILL.md:98.
Read: a 3× disagreement on the same rule — strong evidence these thresholds are heuristics, not measurements. The shared underlying claim is the one to keep: a model should be able to grep a big reference instead of reading it linearly.
4 · Does eval tooling exist?
platform docs"There is not currently a built-in way to run these evaluations. Users can create their own evaluation system."
skill-creator, since 2026-02Ships a complete harness: baseline runs, grading contracts, variance stats, blind A/B, trigger optimization.
Read: docs lag the artifact. The best current documentation of Anthropic's skill-evaluation methodology isn't a docs page — it's this skill's source tree. (The docs' related claim that "you don't need a 'writing skills' skill" sits in the same drawer.)
5 · What is a valid skill, portable vs. local?
validator / open standardSix allowed frontmatter keys; name ≤64 chars kebab-case; description ≤1024, no angle brackets; one SKILL.md per package. Docs add: no "anthropic"/"claude" in names; gerund naming (processing-pdfs) recommended.
Claude Code loaderEverything optional (name defaults to the directory), a dozen extra fields, nested skills load fine, live-reloads on edit — and the flagship repo ignores the gerund advice (skill-creator, mcp-builder, pdf).
Read: two dialects with one syntax. The strict rules are upload-time rules — the moment a skill leaves your machine, the open standard is the contract. quick_validate is best understood as a portability linter.
§10

The distilled doctrine

Strip the machinery away and skill-creator is eight convictions about building instruments for models.

Prose is priced; code is free

Load instructions lazily in three tiers; push anything deterministic into scripts that execute without ever entering context. Two-thirds of skill-creator's own mass never costs a token.

The description is the product

~100 tokens decide every invocation. Put all "when to use" language there, write it pushy against a known undertriggering bias, and optimize it empirically — with a holdout set.

Explain why; shout almost never

Rigid MUSTs are a yellow flag; reasoned instructions travel further with a model that has theory of mind. Reserve capitals for rules that field data proved explanation couldn't carry — and apologize when you use them.

No claim without a baseline

Run with-skill and without-skill in the same turn, three runs each, report mean ± stddev. A skill that can't beat its own absence is a tax, not a tool.

The human reviews before the model corrects

Self-graded quality is circular. Get outputs in front of a person first — through a standard viewer with stable file contracts — then let the model act on their feedback.

Generalize from feedback; hunt near-misses

A skill iterated on three examples must work on a million. Fix categories of intent, not the failing case — and test the boundary with negatives that almost belong.

Bundle what every run reinvents

If all three test transcripts wrote the same helper script, the skill should ship it. The signal for what belongs in scripts/ is empirical, not aesthetic.

Judge blind; diagnose unblinded

Quality verdicts and causal explanations are different jobs that contaminate each other. Split them across agents — comparator picks, analyzer explains.

The larger arc is the one from §03: skill authoring at Anthropic stopped being a genre of technical writing and became an experimental discipline — draft, instrument, measure against a counterfactual, put a human in the loop, generalize, repeat. skill-creator is that discipline packaged to run anywhere Claude does, conversational voice and all. The most honest summary is its own closing line: after 485 lines of protocol, it simply says "Good luck!"
